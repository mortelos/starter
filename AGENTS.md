## Local Rules

1. Use the `mortelos-tooling-setup` skill before portal work when the developer machine cannot yet create, boot or verify a MortelOS host app. Trigger it for missing Herd, PHP, Composer, Node, GitHub access, MortelOS CLI, DBngin, TablePlus, or `mortelos new` setup.
2. Use the `setup-portal` skill for new MortelOS portal requests when available.
3. Keep portal work host-side unless the task is explicitly a package PR.
4. Do not patch `vendor/mortelos/*` or sibling `mortelos/*` package worktrees from a starter task. To change what a package does, plug into its outlets (`php artisan mortelos:outlets:list <package>`) or open a package pull request that adds the missing one; `tests/Feature/OutletsGuardTest.php` fails on the workarounds.
5. Every write is an Action in `app/Actions/<Domain>/` (final, `handle()`, `ABILITY`); a host fact that must be undoable is an aggregate in `app/Aggregates/`, a stored event in `app/Events/<Domain>/` and a projector in `app/Projectors/`. Never `event(new …)` outside an aggregate, never `app/Livewire/`, never `resources/views/livewire/`: pages are `resources/views/pages/<domain>/⚡<name>.blade.php` (`pages::`), shared components `resources/views/components/<group>/⚡<name>.blade.php`. `tests/Feature/ArchGuardTest.php` fails on it; its allow list may only go down.
6. Record package decisions before adding new surfaces.
7. Verify host behavior with `php artisan starter:doctor`, `composer test:arch`, `composer test`, `composer test:browser` (after `npm run build` and, once per machine, `npx playwright install chromium`) and `vendor/bin/pint --dirty` when applicable.
8. Do not use em-dashes in Dutch user-facing prose.
9. Build UI only from `<x-mortel::…>` components; the catalogue is `vendor/mortelos/ui/COMPONENTS.md`. `tests/Feature/UiGuardTest.php` fails on `<flux:` and on raw `<select>`, `<table>`, `<button>`, `<input>` or `<textarea>`. The same test prints hints without failing — a primary button outside the action bar, a disabled primary — and those are questions to answer, not output to scroll past.
10. `laravel/vet` guards `composer install`, `require` and `update`: a package version that `vet.json` does not trust fails the command. Only a new dependency is a reason to stop and ask; clear everything else yourself.
    - **New dependency: ask first.** Before you `composer require` a package that `composer.json` does not list yet, tell the user which package, what it is for and why the installed packages do not cover it, and wait for a yes. That yes covers the packages it pulls in. Installing or updating a package that is already listed, including `mortelos/*` and `laravel/framework`, needs no question.
    - **Clear it with `bin/vet-agent`.** It runs `./vendor/bin/vet` with "Automatically, with my coding agent reading the changes first" and trusts the packages that review passes. Vet has no non-interactive option for that review; `bin/vet-agent` answers its prompts in a pseudo-terminal.
    - **Non-zero exit: review the flagged packages yourself.** Vet's review often flags a package that is fine, so do not hand this to the user. `WARN` means the review could not finish (files over the budget, not text, no answer); if the reviewing agent itself failed (rate limit, timeout), run `bin/vet-agent` once more first. `FAIL` means the review saw a possible risk, which is often ordinary code the package needs, such as an HTTP client that calls a URL or a CLI tool that starts a process. For each flagged package, read what vet reported and the files it named, and compare the old and new version on the package's own repository (`gh api repos/<owner>/<repo>/compare/<old>...<new>` and its release notes). Trust it when the change fits what the package is for and matches its repository at that tag. Stop and tell the user in plain words only on a real red flag: obfuscated or encoded code, code that reads `.env`, keys or credentials and sends them somewhere, a download or shell command at install time, a host that has nothing to do with the package, code that is not in its repository at that tag, or a finding you cannot explain. When every flagged package passes, run `bin/vet-agent --trust-all` and list each one in the pull request with what vet flagged and why it is safe. `--trust-all` trusts every package left in the list, so if you stop on one, do not run it for the others.
    - Then run `composer install` again and commit `vet.json` with `composer.lock`. Never edit `vet.json` or `vendor/composer/installed.json` by hand, and never run `vet --init` or `vet --fresh` to get past a failure.
11. `docs/building-blocks.md` lists what this starter already wires (sign-in and account, tenancy and membership, access and governance, users and invitations, inbox, shell and navigation, events and data, checks and tooling) and where each block lives. Read it before you propose code, together with the `reuse-*` rules in the MortelOS block below. A portal keeps the list current: a change that adds, removes or moves a block updates it in the same pull request.

For current contracts, routes, install steps and troubleshooting, use the documentation site instead of this repository.

# mortelos/agent-standards
## MortelOS Agent Standards

These rules are MortelOS-owned. Treat upstream Laravel, Spatie and community conventions as useful references, but prefer the MortelOS docs, package boundaries and local code patterns when they differ.

### Working Method

- Read the active package `CLAUDE.md` before editing inside a MortelOS package.
- Keep host app work host-side unless the request explicitly targets a reusable package.
- Record package decisions before adding new reusable surfaces.
- Before proposing code, follow Reuse First below.
- Use direct tools for executable actions. Do not report a tool, OS, app, package or browser action as complete until the direct command or tool has succeeded.
- Keep changes scoped to the requested behavior and the package boundary that owns it.
- Verify with the narrowest meaningful commands first, then broaden when behavior crosses package boundaries.

### Reuse First

Rules for deciding whether a change needs new code at all. Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked.

- **reuse-inventory.** Before proposing code, split the change into parts and look up, per part, what already covers it: the host's `docs/building-blocks.md`, the catalogue `vendor/mortelos/agent-standards/resources/mortelos/building-blocks.md`, the installed packages (`composer show 'mortelos/*'`, `composer search mortelos`, `php artisan mortelos:outlets:list <package>`, https://mortelos.com/docs/0/packages), the registrations (service providers, bindings, registries), the active database configuration and, for workflow behaviour, the workflow run involved. The lookup also covers work in flight: the open build plans of the workspace where one exists (at UTEQ: the `.mortelos/BOUWPLAN-*.md` files in the `mortelos/workspace` repository that are not marked done), the open pull requests and recent branches of the app and of the packages involved, and commits on a package's main branch that no tag contains yet. A block found there goes into the reuse table with its state ("on branch X", "PR #N", "plan Y, task N"), and the plan says whether it waits for that work, builds on it, or coordinates with its owner. A missing binding, a wrong setting, or a block that sits on another branch or in a newer package version does not prove that a capability is missing: compare the installed package version with the package source. When the database could not be checked, say so. Check: review.
- **reuse-ladder.** Per part, take the lowest step that works: 1 it already exists and only data or content is needed; 2 a value, right or setting (a policy row, a `tenant_settings` key, a row in an existing configuration table); 3 a process or workflow definition in an existing engine (steps, conditions, recipients); 4 a small class that plugs into an existing extension point (an outlet, a registry, a step handler) through `outlet-first`, or the own tables of an app's domain data, changed through `Mortel\OwnTables` and the generic `OwnTableProjector` (`own-tables`): code or schema, but no new mechanism; 5 a new mechanism or engine, or a table that is not domain data (a second log, version, proposal or settings store). A new table for domain data is therefore not step 5 by itself. The plan or pull request carries a reuse table with one row per part: part, existing block, step, why not lower. Check: the reuse table in the plan or pull request.
- **reuse-code-reason.** Step 5 needs one of three reasons, stated in one sentence: a measured, significant performance gain; a guarantee that must not be configurable (authorisation, tenant boundaries, data integrity, personal data); or a general capability that is really missing, which you build as a reusable block in the package that owns it, through `outlet-first` and a package decision rather than by changing package behaviour directly, so the next case is configuration again. A second engine next to an existing one counts as a cost, not as a reason. Check: the reuse table in the plan or pull request.
- **reuse-db-first.** Customer-, tenant-, role- and feature-specific behaviour lives in the database: rights in policies, mutable settings in `tenant_settings` or an existing dedicated model. Before adding code or file config, verify whether policies, `tenant_settings` or another existing database primitive already expresses the behaviour. `/config` holds static platform configuration only. Code interprets configuration and never hardcodes a customer or role name; stored configuration refers to stable identifiers, not display names. Keep menu visibility separate from capability and data rights, and add no role profile, tenant setting or new authorisation system when existing policies or abilities suffice. A migration is not the source of changeable customer configuration: write it through the Action, admin screen or command that owns that configuration, so authorisation and approval apply, and name that route in the plan. Check: review.
- **reuse-config-limit.** Configuration holds the business rules: when something happens, who reviews or receives it, which text appears, which next step is offered. Code guards authorisation, tenant boundaries, validation and data integrity. Configuration is not a programming language: when it needs nested conditions, or the same configuration shows up a third time, first run `reuse-inventory` again (an existing engine may already cover it), and only then propose the missing block. Test: a different reviewer, recipient or next step within the existing capabilities is possible without a PHP change. Check: review; run the configured workflow to verify the behaviour.
- **reuse-catalog.** A pull request that adds, removes or moves a block updates the list in the same change: `docs/building-blocks.md` for a host block, the catalogue for a package block. The catalogue lists released blocks, and in its section "Announced blocks" the blocks that are decided but not released yet, each with its state (open with the pull request number, in progress, or planned); that row moves to its normal section with the version when the block is tagged, and is removed when the work is dropped. A host's `docs/building-blocks.md` may also list a block that exists only on a branch or an open pull request, with its state, and that row is updated or removed when the work merges or is dropped. Check: review.

### Outlets First

Rules for changing a `mortelos/*` package for a host need. Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked.

- **outlet-first.** Before changing a `mortelos/*` package for a host need, run `php artisan mortelos:outlets:list <package>` and climb the ladder: config, event, registry, contract, view outlet. Only when none fits, open a package pull request that adds the missing outlet (additive, patch release) and plug in from the host afterwards; the behaviour itself stays in the host. Change the package's own behaviour only with a package decision (`mortelos:package-decision`) and only when a second host needs it, it is a bug or security fix, or it concerns the package's own default screens or defaults. Check: `OutletsGuard` (`unknown-outlet`, `concrete-subclass`, `config-set`, `vendor-require`, `vendor-patch`, `vendor-view-copy`).
- **outlet-no-subclass.** Extend only interfaces and abstract classes from a package. A concrete package class is `final`; a host that needs different behaviour binds or decorates the contract outlet. Check: `OutletsGuard` (`concrete-subclass`).
- **outlet-ship.** A package change that adds a public surface (an interface, a registry, an event, a config file, an `<x-mortel::outlet>`) lists it in `resources/mortelos/outlets.json` in the same change, with a one-sentence description and, for a view outlet, its data and default. The manifest entry is the package decision for that surface. Removing or renaming an outlet is breaking. Check: `OutletsManifest::assertValid` in the package tests.
- **outlet-config.** Package settings live in one config file registered with `mergeConfigFrom` and published under a tag; new config files publish under `<package>-config`, existing tags stay. A host overrides platform configuration (`setting-kind`) by publishing that file or through `.env`, never with `config()->set` or by requiring the vendor file. A tenant setting is changed in the database through its screen or proposal (`setting-changeable`), never through `.env`. Check: `OutletsGuard` (`config-set`, `vendor-require`).
- **outlet-view.** A package screen marks each place a host may add to or replace with `<x-mortel::outlet name="<package>.<screen>.<place>" :data="…">` with the default inside; a host plugs in with `Outlet::view`, `Outlet::livewire` or `Outlet::render` in a provider, `replace: true` to drop the default. Data that a Livewire component does not declare as a property is dropped silently, so declare every key you pass. Hosts never copy or publish package views. Check: `OutletsGuard` (`vendor-view-copy`, `unknown-outlet`); `UiGuard` hint for an outlet name without the package prefix.
- **outlet-package-pr.** When a package needs a new outlet, the pull request contains only the outlet, its manifest entry and a test; it does not carry the host feature. Check: review.

### Package Scope

Rules for deciding whether something is a package and what it may own. Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked.

- **package-when.** Something becomes a package for one of three reasons only: it connects one external service (`channel-*`), it is a platform capability every app needs (`framework`, `ui`), or a second app needs it now. Everything else stays in the app. One customer's process or rules are configuration or app code, never a package, and a package that would hold only settings or a single screen is not a package. Test: say in one sentence, without "and", what the package does; when you cannot, it is two packages or part of it belongs in the app. Check: the package decision (`mortelos:package-decision`) names the reason.
- **package-owns.** Dependencies point one way: app, then packages, then `framework` and `ui`. A package never refers to an app, a customer or a role name, and owns no table for what the framework already models: a connection is a `channels` row, content is a stored event with a projection, a setting is a `tenant_settings` key, a right is a policy. Check: review; a package's `composer.json` requires no app.

### Settings And Configuration

Rules for deciding where a value lives, who changes it and how. Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked.

- **setting-kind.** Before adding a value, decide who changes it and when; that decides where it lives. A fixed rule that changes only with a release is code (a constant or enum). Platform configuration, changed with a deploy by whoever runs the installation (hosts, paths, binaries, queues, timeouts, base URLs, our own API keys), is a key in the package config file, read from `.env` where it differs per environment. A tenant setting is a business rule one customer may want different from another (thresholds, recipients, texts, schedules, toggles, limits, model choice): it lives in `tenant_settings`, with its default in the config file. A business rule with a clear owner at the customer may instead live in a fixed `setting:<key>` block on its knowledge page: the approved page is then the source and the `tenant_settings` row is derived from it, whoever may read the page sees the value, and a change always goes through the Knowledge proposal route, never a direct write; technical switches stay in the database. A user preference applies to one user only. Rights are not settings but policies: data too, which an admin changes on the policy screen or through a chat proposal (`mortelos/policy-studio`). Process definitions live in their engine (workflows, automations). Operational state a job keeps for itself (a cursor, a last-run marker) is not a setting and is never shown as one. Test: would one customer want this value different from another? Then it is a tenant setting. Check: review; the plan or pull request names the kind of every new value.
- **setting-locked.** A key whose wrong value could open a tenant boundary, the sandbox, authorisation or data integrity is platform configuration only and is never read from the database, not even as an override. The package's settings class lists those keys as config-only, as `SidecarSettings::CONFIG_ONLY` does. Check: review of the config-only list.
- **setting-secret.** A secret of our own account (the platform's API key) lives in `.env` and is read through config. A credential that differs per tenant or that a customer manages themselves (their own Moneybird, Google or GitHub account) is entered on a screen and stored encrypted in the database: on the owned `channels` row (`credentials_reference`) for a connection, or in the host's encrypted secrets table (such as `app_secrets`). It never lives in `.env`, config, `tenant_settings`, entity attributes or a stored event payload. Check: review.
- **setting-layers.** A value resolves from general to specific, and the most specific layer that has a value wins: code default, package config, host config or `.env`, tenant setting, user preference. A key is overridable only at the layers it allows; a tenant setting is not a user preference unless the package says so. Read a setting where it is used, inside the tenant context of the request or job. Never copy tenant values into `config()`: a long-running process (a queue worker, Octane) keeps the value for the next job or request, possibly of another tenant. Check: `OutletsGuard` (`config-set`); review.
- **setting-one-reader.** A package reads its tenant settings in one settings class (such as `SidecarSettings` or `BankSettings`), which delegates to the framework's `Settings` building block. Register key definitions with `SettingsCatalog`; new keys start with the package name (`<package>.`). The framework owns defaults, type checks, scoped tenant-and-branch snapshots and table checks through `Mortel\Support\SchemaCache::hasTable()`. Never keep tenant values in a singleton or a static property. No code outside the framework queries `tenant_settings` directly. `ReadTenantSetting` and `WriteTenantSetting` are used only in the settings class or for operational job state with a `settings-guard: operational <reason>` marker. Check: `SettingsGuard`; a test calls `SettingsCatalog::assertValid()`.
- **setting-changeable.** An authorised person changes a described, unlocked database key without a deploy or code: directly on its settings screen through `ChangeTenantSetting`, with a stored event and undo, or through a stored proposal when the key requires approval. The AI always creates a stored proposal, never a direct change. A page key is changed only through an approved proposal on its knowledge page; nobody writes it directly, even with the write ability. Whoever may read the page sees the value in every view, including history, cards and AI context. Never seed or migrate a changeable customer setting (`reuse-db-first`). A pull request that adds a tenant setting names the screen or proposal route that changes it. Check: review of the pull request; tests cover direct changes and undo for database keys, refusal of direct changes for page keys, and page read access for displayed values.
- **approval-one-route.** Everything that requires approval goes through the Knowledge engine (`mortelos/knowledge`). A package or app adds a target to that engine, never its own proposal or approval engine. Check: review traces each approval entry point through `mortelos/knowledge`; a Feature test proves that the change cannot apply before approval.
- **setting-opt-in.** A new setting defaults to today's behaviour, and a new capability stays off until someone turns it on for a tenant, so a release never changes what an existing customer sees through a default. Changing an existing default is a package decision and is named in the pull request. Check: a test asserts that the default keeps the old behaviour.

### Laravel And PHP

- Use strict types in PHP files.
- Prefer typed constructor promotion, readonly value objects and `final` classes; a class is non-final only when it is an abstract class or interface listed as a contract outlet in `outlets.json`.
- Every write path is an Action in `app/Actions/<Domain>/`: a `final` class with one `handle()` and a `public const ABILITY` it checks before it mutates anything. It takes the actor as a `Mortel\Support\Actor` parameter and returns a `Mortel\Actions\ActionResult`. Call framework Actions through `handle()` only: `execute()` is the old name that still exists on 23 framework Actions, and new code never calls it. A Livewire method, controller, job or console command validates input, calls the Action and shows its result; it never writes a model, fires an event or calls an external API itself. Check: `ArchGuard` (`write-outside-action`, `action-shape`).
- Screens, API endpoints, agent and MCP tools, chat and bridges are entry points to the same Actions and readers. Validation, authorisation and business rules live in the Action: a rule that only a screen enforces is a bug, because the next entry point skips it. Check: review.
- `app/Support` holds pure classes only: value objects, readers, formatters and resolvers. Nothing there calls `save`, `create`, `update`, `delete`, `DB::statement` or `event(`. Behaviour that writes is an Action; behaviour that reacts to a stored event is a projector or reactor. Check: `ArchGuard` (`write-outside-action`, `event-outside-aggregate`).
- Keep Eloquent models strict: define relationships, casts and fillable or guarded behavior intentionally.
- Prefer immutable dates for domain data and time-window calculations.
- Fail loudly for impossible states with small exceptions or validation results instead of silent fallbacks.
- Avoid global helpers for domain logic unless the helper is already an established local convention.

### Host State And Events

- A host fact that must be undoable or auditable is an aggregate in `app/Aggregates/`, a stored event in `app/Events/<Domain>/` and a projector in `app/Projectors/` that writes the read table. The read table is a projection: a replay (`php artisan event-sourcing:replay "App\Projectors\…"`, or `Spatie\EventSourcing\Projectionist::replay()` in a test) must reproduce it from the events alone, so nothing but the projector writes it. Check: a Feature test that rebuilds the projection and compares the rows. The domain tables of an app are the exception to "a projector per read table": the generic `Mortel\OwnTables\OwnTableProjector` writes them (`own-tables`, `own-tables-projector`), and the app writes no projector of its own for them. Exception for page-backed tenant settings: the approved page is the source, and its derived `tenant_settings` row is written in the same transaction as the page version. No projector writes that row; rebuild it from the approved pages, never by event replay. Every package with page keys has a test that rebuilds their rows from the pages. This exception applies only to page keys; other host projections still rebuild from events alone.
- Record a stored event only through `recordThat()` in an aggregate. Never `event(new …)` a `ShouldBeStored` event from an Action, a Livewire component, a job or a controller. Never fire a framework event by hand (`ChannelUpdated`, `EntityUpdated`, `RoleCreated`, …): call the framework Action that owns it (`Mortel\Actions\…`), which goes through its aggregate. Check: `ArchGuard` (`event-outside-aggregate`) and the `GovernedModelWriteRule` in PHPStan (`vendor/mortelos/dev-tools/extension.neon` with a published `config/spine.php`). The attribute `#[GovernedWriter]` (`mortelos/app-standards`) sanctions a writer of a governed model that is outside `Mortel\OwnTables`; never put it on an Action that writes an own domain table, because only the projector writes those (`own-tables-projector`).
- Every stored event implements `Mortel\Contracts\ProvidesStoredEventMetadata` (`storedEventType()` as `<domain>.<thing>.<past tense>`, `storedAggregateType()`) and is registered under that type in `event-sourcing.event_class_map`, so a renamed class does not break a replay. Check: `ArchGuard` (`event-metadata`).
- Every mutating Action returns a `Mortel\Actions\ActionResult` with status `done`, `approval_needed`, `failed` or `skipped` (constructors `ActionResult::done()`, `approvalNeeded()`, `failed()`, `skipped()`). When the change can be reversed, the result carries a `Mortel\Actions\Undo`: `Undo::of(CounterAction::class, [...params], validUntil)`, where `action` is the FQCN of the counter-Action. When it cannot be reversed, the docblock says why (sending, paying, publishing). For a change on own tables the counter-Action is the framework's `RevertOwnTableChanges`, offered as `$recorded->undo()` (`own-tables-undo`); do not write one by hand. Register the counter-Action in a service provider with `app(UndoRegistry::class)->register(CounterAction::class, fn (array $params, Actor $actor): ActionResult => …)` (`Mortel\Actions\UndoRegistry`); the screen renders the message and the undo button from the result, never from its own state, and rolls back with `app(UndoRegistry::class)->undo($result->undo, Actor::current())`. The undo recipe lives in the result, not in the event metadata: the counter-Action records its own stored event, and that event is the audit. Check: a Feature test asserts the result status and, for a reversible change, runs the undo through `UndoRegistry`.
- Every actor is a `Mortel\Support\Actor`, with four forms: `Actor::user($user)` (the actor text is the bare user id, no prefix), `Actor::agent($runId, $onBehalfOf)` (`agent:<run-id>`), `Actor::system('scheduler')` (`system:<process>`) and `Actor::bridge('telegram')` (`bridge:<name>`). `Actor::current()` is the logged-in user. Fill `Mortel\Support\EventContext` (actor, reason, org, branch) around every Action that records an event with `app(Mortel\Support\EventContext::class)->within($actor, $reason, fn () => …)`, which restores the previous context afterwards so a later step in the same request does not inherit it. Never call `fill()` and restore by hand. An empty actor is a bug, not "the system did it". Check: a Feature test asserts the actor on the stored event.
- A host ability (the `ABILITY` constant of a host Action, for example `invitations.manage`) gets its policy in scope `Mortel\Enums\PolicyScope::Action`, where `Mortel\Actions\Policies\CheckPolicy` evaluates it. Never use `PolicyScope::AgentTool` for a host ability. Check: a Feature test that checks the ability with and without the policy.

Worked example in the starter (v0.11.0+): `app/Actions/Invitations/InviteUser.php`, `app/Aggregates/InvitationAggregate.php`, `app/Events/Invitations/InvitationCreated.php`, `app/Projectors/InvitationProjector.php` and the users page that calls them.

### Own Tables

Rules for the domain data of an app: the rows with typed columns and real relations that make the app what it is (phases, material lines, work packages). Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked. Mechanics and setup: `vendor/mortelos/framework/docs/own-tables.md`.

- **own-tables.** The domain data of an app lives in its own tables, and a row changes only through an aggregate event that carries the state before and after. An Action calculates, puts every model it changes on a `Mortel\OwnTables\ChangeSet` (`save()`, `delete()`) and records one event that names the intention, through `Mortel\OwnTables\OwnTableChanges::record()` on an aggregate with an `AggregateUuid::for()` id. The event extends `RowChangesEvent` and holds `changes[]`: for every row it touches the complete row before and after. Give every own table an integer `revision` column, the collision check of an update. Never `save()`, `update()`, `delete()`, a bulk `update()` or `DB::table()` write on an own table, and never rely on `ON DELETE CASCADE` for a change: load the rows and add them to the `ChangeSet`, so the event is complete. Check: a Feature test asserts the event and its `changes[]`; `php artisan mortel:projection:rebuild --host --verify` reports no differences; `GovernedModelWriteRule` with the own-table models in `governed_models` (`app-standards`, spine contract), without `#[GovernedWriter]` on any Action that writes them.
- **own-tables-projector.** The generic `Mortel\OwnTables\OwnTableProjector` is the only writer of own tables: register it in `event-sourcing.projectors` and list its tables, parents first, under `mortel.projections.tables`. An app writes no projector, observer or listener of its own for these tables. A projector of an app is for a read model that is not an own table (`Host State And Events`). Check: three layers that each cover part of it: the PHPStan rule `GovernedModelWriteRule` (`mortelos/dev-tools`) flags a direct write to a model listed in `spine.governed_models`; the opt-in runtime guard of the framework (v0.7.86 and v0.8.83: `mortel.own_tables.write_guard => true` with the own tables listed in `mortel.own_tables.tables`) throws on a direct SQL write to those tables in local and testing and logs a warning in production, while the projector, configured `spine.writers`, migrations and seeders pass; turn it on for every own table (`ArchGuard` does not check this, it allows writes in Actions, aggregates and projectors); and afterwards `php artisan mortel:projection:rebuild --host --verify` finds the rows that did not come from events. A Feature test rebuilds the tables from the events and compares the rows.
- **own-tables-undo.** Undo of a change on own tables is the counter-event of the framework: return `$recorded->undo()` in `ActionResult::done(..., undo:)` and roll back through `Mortel\Actions\UndoRegistry`. It refuses when a row no longer equals its state after the change, and it records its own event, so undoing the undo is redo. Offer the recipe only to whoever may act on that part, and check that right before calling the registry. Do not write a counter-Action that edits rows by hand. Check: a Feature test runs the undo, and a second test shows the refusal when someone changed a row in between.
- **own-tables-no-log.** An app keeps no log, revision, version or history table of its own for domain data (no `activity_log`, `*_revisions`, `*_versions`, `*_changes`), and no proposal store of its own: the `events` table is the history, and open proposals are `inbox_items`. What is deliberately kept outside the events (chat conversations, cache, queue, sessions, the tables of Laravel and packages) is named in the plan with its reason. The archive of the history of a previous app is a read-only table that is imported once (`import-events`). Check: review of the migrations.
- **own-tables-or-entities.** `entities` is for records that users shape themselves (a type with an attribute schema they define) or that are shared widely (visibility, links, search, lists, the record page). A table with typed columns and relations that one app's code owns is an own table, also when a first version would fit in `entities`. Moving later from one to the other changes the data, so decide it in the plan and name it in the reuse table. Check: the reuse table in the plan or pull request.

### Bringing Data Over

Rules for an app that moves to MortelOS and brings its existing data along. Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked. Setup, the definition class and all options: `vendor/mortelos/framework/docs/legacy-import.md`.

- **import-command.** Existing data is brought over with `php artisan mortel:legacy:import` and nothing else: no seeder, one-off script or hand-written copy command. The app writes one definition class (`LegacyImportDefinition`) that says what comes over: tables with `TableMap`, aggregates with `AggregateMap`, files with `FileMap`, its own checks, and a mapper only where the schema really differs. Everything is deterministic: the same source gives the same result. Check: `mortel.legacy_import.definition` points at the definition, and the plan names the command as the only route.
- **import-source-target.** The source is read only: a restored copy of the old database, opened through its own connection (`legacy`) with a database user that may only read; the command refuses a connection that may write. The target database is always empty: the command refuses a target that holds rows of the definition, begin-events or the id map, and never merges with a database in which people have worked. After a failed run, fix the cause, empty the target (`migrate:fresh`, on a target database that has never been used, never on one that people work in) and run again. Check: the command's own refusals; a Feature test with a source that may write is refused.
- **import-events.** Per aggregate the import records one begin-event, `<domain>.<type>.imported`, with every row of that aggregate as a create (`before` null), actor `system:legacy-import` and the reason of the definition; the generic `OwnTableProjector` writes the tables, so a rebuild reproduces them. Own tables keep their ids; where an id changes (an integer user id becomes a ULID), every reference goes through the id map `legacy_import_ids`. A table that stays outside the events is marked `outsideEvents()` and its reason is in the plan. Check: `mortel:projection:rebuild --host --verify` reports no differences after the import.
- **import-checks.** A run is checked in three layers and fails on any deviation: counts and checksums per table (and every file reference with its hash), then the events against the tables (`mortel:projection:rebuild --host --verify`), then the app's own business checks (`LegacyImportCheck`: a recalculation changes nothing, totals are equal, a fixed search finds the same records). The report (`report.json` and `report.md`) holds tables, keys, columns, counts and durations and never the content of a row; an exit code other than 0 is a failed import. Check: the exit code of the command and the report of the run.
- **import-rehearsal.** From the first domain onwards the import runs every night on a fresh copy of production, on an empty database, and every domain extends it with its mapping and checks. A red night is an open finding. The real switch is the same command on the last dump, with the same checks. Check: the report of the last night is `passed`.

### TALL And UI

- UI is built exclusively from `<x-mortel::…>` components (package `mortelos/ui`). Never write `<flux:…>` directly and never write raw `<select>`, `<table>`, `<button>`, `<input>` or `<textarea>`. Icons are `<x-mortel::icon name="…" />`.
- **Kit first.** Before building any UI, read `vendor/mortelos/ui/COMPONENTS.md`: its decision table names the component for each need, and `vendor/mortelos/ui/docs/recipes.md` has copy-ready screens. Use only the props, values and slots the family pages list; never invent one.
- No UI components of your own in an app or package: taste is set with the theme tokens and `class` (`COMPONENTS.md`, "Theming"). The one exception is an application component, a Blade component specific to one app or front-end package: only `<x-mortel::…>` tags and HTML, no network call, no `$wire` and no `wire:` attribute of its own besides `wire:key` and `wire:navigate`, no `<script>`, no Flux, and field roles as props (`amount`, `date`, `tone`), never business names. Check: `UiGuard::assertAppComponents()` on the app's component folders.
- A missing generic piece is asked of the kit: open an issue or pull request on `mortelos/ui` that names the need and the screens, and until it ships compose the screen from existing `<x-mortel::…>` components in the page view itself. Never build a reusable UI component in an app or a package. For UI the kit does not wait for a second user; elsewhere the second-user rule still decides rung 7 of the outlet ladder.
- Colours come from the kit's theme tokens (`text-muted-foreground`, `bg-muted`, `border-border`, `text-destructive`), never palette pairs such as `text-zinc-500 dark:text-zinc-400`.
- Fast screens: follow the speed rules in `COMPONENTS.md` ("Fast screens") and the "Livewire 4" rules below.
- The action that moves a screen forward is its only `variant="primary"` and lives in `<x-mortel::page-actions>`, or in the `actions` slot of `<x-mortel::page-header>` on a list page. A form may have its own `type="submit"` primary. Optional actions (send a message, add a document, export) are never primary.
- Row actions in a list or table are never `variant="primary"`: use the default, `filled` or `ghost` variant, so the screen keeps its one primary action.
- A blocked primary action explains, at the button, why it is blocked and what unlocks it: use `<x-mortel::page-actions blocked="…">` and put the unlocking action in its `unlock` slot. Never render a disabled primary button without a reason.
- Status copy and the primary action must agree: do not write "ready" or "done" while the next step is still blocked.
- Pick the purpose-built component before composing wrappers: a choice with more than about seven options or free-text search is `<x-mortel::select searchable>` (never a plain select); multi-choice is `multiple`; an empty list is `x-mortel::empty`; a page title with buttons is `x-mortel::page-header`; key figures are `x-mortel::stat.grid`; a filter row is `x-mortel::filters`; tabs are `x-mortel::tabs`. The decision table in `COMPONENTS.md` lists them all.
- The `UiGuard` test fails the build on violations; do not add `{{-- mortel-guard: ignore --}}` without saying so in the PR description. It also prints hints without failing (a primary button outside the action bar, a disabled primary): answer the hint or say why it does not apply, never leave it unread. It also runs `UiGuard::assertFluxFree()`: since `mortelos/ui` 0.6 the own kit is the only implementation and there is no kit switch. An app or package still on Flux follows the steps in `vendor/mortelos/ui/docs/migration.md` and lands on 0.6.
- Alpine bindings on an `<x-mortel::…>` tag use the long form (`x-bind:class`, `x-bind:id`, `x-bind:aria-selected`); the shorthand `:attr` is a Blade dynamic prop there and breaks the page. Never reference Flux views as strings either (`flux::…` in `@include` or `x-dynamic-component`).
- Keep Blade components presentational; move authorization, orchestration and state transitions into PHP classes.
- Build dense operational screens for portal workflows. Avoid marketing-page composition for admin or back-office tools.
- Preserve accessibility basics: labels, keyboard paths, visible focus states and meaningful empty states.
- Do not add visible instructional text about implementation details, styling systems or agent workflow.

### Livewire 4

Rules for Livewire 4.4 views. Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked.

- **island-when.** Wrap a part that has its own actions or poll in `@island(name: '…')` when nothing outside it has to change after those actions. Check: one interaction there sends 1 POST whose response holds only that island (`islandFragments`, no `effects.html`).
- **island-stale.** Never render outside an island, as `{{ $property }}`, a property that an action inside the island writes: bind it with `wire:model` or `$wire`, or move that markup into the island. An `<x-mortel::…>` component that shows such state (`page-actions` with `blocked`, `stat`, `page-header`) sits inside the island. Check: grep every property the island's actions write.
- **island-always.** Give an island `always: true` when anything that renders the whole component changes what the island shows: an action outside the island, an `#[On]` listener, or `Livewire::test()->call()` in a test (without it the island comes back empty with `mode=skip` and `assertSee` fails). Check: a Feature test calls the action (or dispatches the event) and asserts the island's text.
- **island-place.** Never put `@island` inside `@foreach` or `@if`, and never in the template of an `x-mortel::…` or other anonymous Blade component; islands live in the Livewire view (inside the slot of an `<x-mortel::…>` tag there, such as `card` or `tabs.panel`, is fine). Inside an island use only `$this`, public properties and variables defined in the island. Check: the `UiGuard` hint for an island in an anonymous component; no hint covers `@foreach`, `@if` or outside variables, so read each `@island` for them.
- **island-trigger.** Trigger an island from outside with `wire:island="name"` on the element; from Alpine code that is not a button click (a key handler, a callback) call `$wire.$island('name').method()`. A bare `$wire.method()` from Alpine renders the whole component and skips the island, so the island does not update. Check: the `UiGuard` hint for unknown island names, and an island-only POST in the browser test.
- **island-concurrency.** An island action runs in its own request queue and does not wait for actions outside the island (measured on Livewire 4.4.6: an island action answered after 1201 ms while a 2530 ms outer action still ran), so two requests of one component can write the same row at once and the last write wins. When an action stores a value computed from data it just read, read and write in `DB::transaction()` with `lockForUpdate()`, or use one atomic query: `increment()`, or an `update()` whose `where` holds the expected old value. Wrong: `$doc->version++; $doc->save();`. Right: `Document::whereKey($id)->increment('version');`. Exception: a table of the app's domain data (`own-tables`) is never written with `increment()` or a direct `update()`. There too the Action calculates, changes the rows through `ChangeSet` and `OwnTableChanges::record()`, and concurrent writes are handled by the Action itself: two requests that record on the same aggregate conflict on its version, which `Mortel\Support\RetryOnAggregateConflict::run()` retries, so retrieve the aggregate and read the rows inside its callback; a row that changed since it was read is refused through its `revision` column (`OwnTableConflict`). `increment()` and `update()` stay allowed on tables that are deliberately outside the events, such as counters, caches and logs. Check: grep the actions of each component with an `@island` for a stored value computed from a read outside a locking transaction; on an own table a direct `increment()` or `update()` is a finding (`own-tables`).
- **click-server.** A button that runs PHP uses `wire:click` (the kit button shows the loading state and the island follows from the button's position), not `x-on:click="$wire…"`. A click that only opens, closes, toggles or selects something never calls PHP: no `wire:click` to a method that only assigns UI state, and no `wire:click="$set(…)"` or `"$toggle(…)"`, which are round trips too. Keep that state in Alpine (`x-data`, `x-show`), or write `x-on:click="$wire.open = true"` with `wire:show="open"` when PHP must read the value with the next action: a `$wire.prop =` write sends nothing by itself. Check: the `UiGuard` hint `ui-only-click`; the browser test counts 0 POSTs for that click.
- **lazy-placeholder.** A dashboard widget, a tab panel and any section with its own query or API call is a child component that loads `defer` (in view on load) or `lazy` (below the fold); several that load together use `#[Lazy(bundle: true)]` or `defer.bundle`. A slow part (a query or API call in `mount()` or render) is `defer` when it is in view on load and `lazy` below the fold, and always has a placeholder: `<x-mortel::placeholder height="…">` at the height of the content; it renders a `div`, so the component root is a `div` too (Livewire needs the same root tag). No select, tabs or form in a placeholder. Content tests of a lazy component use `Livewire::withoutLazyLoading()`; a lazy or deferred island always renders its placeholder first, so assert its content in the browser test. Check: layout shift below 0.01 in the browser test.
- **loop-key.** The outermost element of each iteration of a `@foreach` in a Livewire view has a `wire:key` (on a plain element, not on an `x-mortel::select` with a `label`, whose key lands on an inner element) built from a stable record id, never `$loop->index`, and `wire:model` inside a loop binds by that id (`rows.{{ $row->id }}.field`), not by position. Check: grep the loops.
- **poll.** `wire:poll` sits inside an `@island`, always, and has an integer and a unit (`.10s`, `.750ms`), the longest interval that works, and `.visible` unless the element can never scroll out of view. A poll under 5 s needs a reason in the pull request. For "is it done yet" states (a thinking indicator, job progress) do not poll at all: stream from the action that does the work with `$this->stream(to: …)`, or listen to a broadcast event. When the polled data is shown outside any possible island, poll a `#[Renderless]` check action that calls `$this->js('$wire.$refresh()')` only when something changed. No untargeted `wire:loading` in a polling component. Check: the `UiGuard` hints `poll-outside-island`, `poll-fast` and `poll-not-visible`; `LivewireMonitor::summary()` in the browser test.
- **live-state.** Show state that changes elsewhere (OAuth in another tab, a job, a webhook) from its source on every load, never from a copy stored when the view was made; while waiting, listen for its event or follow `poll`, and stop when done. Check: a test with stored "pending" and source "done" shows "done".
- **renderless-async.** Put `#[Renderless]` and `#[Async]` only on actions that change nothing shown in Blade. An action that changes something shown but updates the browser itself (`row-action`) calls `$this->skipRender()` instead and stays out of `#[Async]`. Use `#[Computed(cache: true)]` only for data that is the same for every user and tenant: its cache key is the component name and method, or a constant `key:`, shared by everyone. For per-user data use `persist: true` or `Cache::remember()` with the user or tenant id in the key. Check: a `#[Renderless]` action's response has no `effects.html`; an `#[Async]` action writes no property shown in Blade (grep); grep `cache: true` and confirm the data is global.
- **snapshot.** No public property for data that only `mount()` needs (keep it a `mount()` parameter) or for large derived HTML (make it `#[Computed]`): public properties travel both ways in every request, polls included. No public property typed as a model, an Eloquent `Collection` or a paginator, and no public array filled from a query: Livewire re-runs the query on every hydrate (`docs/properties.md:219-223`) or ships the whole array both ways. Keep the id (`#[Locked] public int $itemId`) and read the record or list in a `#[Computed]` method. Check: the `UiGuard` hint `heavy-public-prop`; a Feature test asserts the size of `json_encode($component->snapshot)`.
- **loading-state.** `<x-mortel::button>` already shows a loading state for `wire:click` and `type="submit"`. Elsewhere use the `data-loading:`, `in-data-loading:` or `has-data-loading:` variants on the element that triggered the request or its container; they need no `wire:target` and do not move layout. A `wire:loading` always has a `wire:target`. Never add `wire:loading.attr="disabled"` to a submit button of a `wire:submit` form: Livewire already disables the form during the request. In a long list of identical row buttons, `:loading="false"` leaves the spinner markup out. Check: the `UiGuard` hint `untargeted-loading`; layout shift around the click below 0.01.
- **root.** A Livewire view renders exactly one root element with nothing before it, not even `<style>` or `@once`; component CSS goes in `@assets`. Check: a Feature test finds `wire:id` on the intended root element.
- **navigate.** Init code that must run again after `wire:navigate` listens to `livewire:navigated`; JS that mounts a third-party widget on Livewire DOM destroys it on `livewire:navigating`. `$this->stream()` always names its target (`to:` or `->to()`) and escapes its content with `e()`. Check: after navigating away and back the widget exists once and the console is clean; grep `stream(` for a target.
- **package-component.** Package components are single-file components in `resources/views/components/⚡<name>.blade.php` of the package (sub-folders allowed), registered with `Livewire::addNamespace(namespace: '<unique>', viewPath: '<package>/resources/views/components')`; the component name stays `<namespace>::<name>`. No `resources/views/livewire/` in a package. Check: grep `addNamespace(` in the workspace and in `vendor/` of the host apps; the namespace occurs once and `viewPath` points to the package's `resources/views/components`; grep `resources/views/livewire` in packages returns no matches.
- **layout.** A host page is a single-file component in `resources/views/pages/<domain>/⚡<name>.blade.php`, routed as `Route::livewire('/path', 'pages::<domain>.<name>')`; a shared component is `resources/views/components/<group>/⚡<name>.blade.php`; layouts stay in `resources/views/layouts/` (`layouts::app`). No `resources/views/livewire/`, no classes or traits under `app/Livewire/`, no `Livewire::addNamespace()` in a host for its own views. A page above about 300 lines splits into components, never into traits. Check: `ArchGuard` (`livewire-path`, `livewire-class`, `livewire-zap`) and the `UiGuard` hint `page-size` for a routed page over 300 lines without comments.
- **navigate-link.** Every internal link in a Livewire layout has `wire:navigate`: plain `<a>`, `x-mortel::button href`, `link`, `sidebar.item`, `navlist.item`, `navbar.item`, `breadcrumbs.item` and `menu.item`. The bare `navigate` prop does nothing today (it renders `navigate="navigate"`). Main navigation uses `wire:navigate.hover`; the sidebar or any part that must keep its state across pages sits in `@persist('name')`. Leave out `wire:navigate` only for downloads, OAuth and logout routes, `target="_blank"` and pages outside the Livewire layout. Check: the `UiGuard` hint `link-without-navigate`; after a click in the browser test the document is not reloaded (`window` marker survives).
- **no-refresh.** Never re-render a whole component from a timer, a visibility event or `$this->js('$wire.$refresh()')`. Refresh what changed: an island (`wire:island="name"` on the trigger, `$wire.$island('name').$refresh()` from Alpine), or listen with `#[On('…')]` to the event that changed the data. `$refresh` inside an island is fine; it renders only that island. Check: the `UiGuard` hint `refresh`.
- **model-live.** Text inputs bind with plain `wire:model` (sent with the next action) or `.blur`. Use `.live` only where the screen must change while the user types (search, live preview), and then with `.debounce.300ms` or more; `.live` alone already waits 150 ms per pause and still sends a request per pause. Selects, checkboxes, radios and switches may use `.live` without debounce. Check: the `UiGuard` hint `live-text`.
- **fire-and-forget.** An action that only records something (a read marker, last seen, a click log, analytics) and changes nothing shown in Blade is `#[Renderless]` plus `#[Async]`, or is called as `wire:click.renderless.async`; when JavaScript needs its result it is `#[Json]`. The limits of `renderless-async` apply. Check: the response has no `effects.html` and does not wait for other requests (browser test).
- **row-action.** A change the user makes to one row, card or cell of a list, table or board (another person, a status, a tick, a number) shows the new value in the browser at the click, before the server answers, and the action answers without rendering the whole component: `$this->skipRender()` with a plain return of that row only (its HTML rendered in the component's view context, or its data), plus the fresh revision. Keep the old value in the browser and put it back with a notice when the action fails or conflicts. Render the whole component, after the row already shows, only when the change moves the row to another group, column, tab or page, or takes it out of the view. Read only the changed rows on the server: no counts, facets or other rows to answer a row action, and never the whole screen twice. Do not use `#[Async]` or `#[Json]` for it (it changes what is shown and must stay in order); `skipRender()` keeps the queue. Livewire 4 has no island per row (`island-place`) and a child component per row costs a snapshot and mount per row: neither replaces this. Check: the browser test declares the interaction with `LivewireMonitor::expect(..., visible: '<expression>')` (mortelos/ui 0.6.48 or later), which holds the POST and requires the new value within 100 ms; the POST has `html: false` and answers under 30 KB.

### Verify UI Changes

- A UI change is done when its verify run is green: run `vendor/bin/pest --filter='UiGuard|ArchGuard|OutletsGuard'`, then the browser test of every screen you touched. Fix what fails and run again until green; never report a UI change as done before that. `UiGuard` also prints Livewire hints without failing: fix each hint, or name it and the reason in the pull request.
- Every screen you touch has one browser test that opens it with `Mortelos\Ui\Testing\LivewireMonitor::visit()` and declares each interaction with `LivewireMonitor::expect()`: the exact number of Livewire POSTs (0 for an action that only changes the browser) and the island when one is used (with `islandMode: 'append'` or `'prepend'` for an island that adds to its content instead of replacing it). `expect()` counts until the page has been quiet for `quietMs` (750 by default): on a page with a debounce, pass a `quietMs` larger than the longest debounce, or the debounced POST is not counted and a budget of 0 passes falsely. The helper also requires 0 console errors, warnings and JS errors, every Livewire POST of the interaction answered 200 (assert `status` of load and poll POSTs from `summary()`), layout shift below 0.01, no ARIA reference to a missing id, no duplicate id, and a screenshot. An interaction that changes a value the user sees (a row action, a toggle, a tick) also passes `visible:`, a JS expression true once the screen shows the result: `expect()` holds its POSTs and requires the result within `visibleWithinMs` (100) of the input, so the screen cannot wait for the server (`row-action`). Add or update that test in the same change.
- `expect()` does not count requests that only run `wire:poll`. Check a poll with `LivewireMonitor::summary()`: during a measured window each poll sends at most one POST with `poll: true` per interval, plus one (tell polls apart by `calls`). Response size and server time (`ms` per POST) are reported, not budgeted, because test machines are shared; click → visible is budgeted because it does not depend on the server. An island response larger than the full render means the island does not pay off, and a POST with `html: true` after a row action breaks `row-action`.
- Put the helper's summary lines and the screenshot paths in the pull request description. If a budget cannot be met, name the budget and the reason; never loosen a budget silently.
- A repository without `pestphp/pest-plugin-browser` (no browser job) runs only `UiGuard`, skips the browser test and names in the pull request the checks that did not run.

### Security

- Validate and authorize at the boundary before mutating state.
- Treat tenant, organization and branch identifiers as scoped data. Never trust request input to select a tenant boundary without authorization.
- Treat user identity, tenant membership and tenant role assignment as separate authorization facts. When `tenant_user` exists, require an explicit row for the active tenant; never infer membership from `users`, `role_user` or a default `member` role.
- Never commit secrets, customer data, API tokens, private keys or local environment values.
- Fake external HTTP, mail, queue, notification and AI calls in tests unless the test explicitly verifies an integration boundary.
- Keep destructive Artisan and database operations guarded in production.

### Version Control And Review

- Keep commits and pull requests focused on one behavior change.
- Explain package-boundary decisions in the change when code moves between host and package.
- Prefer tests that describe user-visible behavior or package contracts over snapshots of incidental implementation.
- Do not rewrite unrelated user changes in a dirty worktree.

### Tests And CI

Keep local tests focused and CI suited to the system's users. Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked.

- **ci-local-tests.** Several agent sessions share one machine: always pair `--parallel` with `--processes=4` or fewer, never use `--parallel` alone. Before a pull request, run the test files you touched, the tests of directories you changed, and the architecture and UI guards when they apply. The full suite runs in CI on every pull request; run it locally only when the app has no working CI. Check: review.
- **ci-runner.** The runner follows who uses the system; ask at the start of a new app. Systems UTEQ uses itself use `runs-on: [self-hosted, uteq-dev]` (the UTEQ dev-server, only private repositories in the GitHub organisations `uteq` and `mortelos`). Systems of a client, partner or anyone else use GitHub-hosted `ubuntu-24.04`, on the owner's Actions minutes. Do not change an existing app's runner yourself; propose it to its owner. Check: review.
- **ci-trigger.** Pull request test and analysis workflows cancel the previous run of the same ref: use `concurrency:` with `group: ${{ github.workflow }}-${{ github.ref }}` and `cancel-in-progress: true`, also on `main` when it is tested after a merge. Deploy and release workflows never stop halfway: use `cancel-in-progress: false`. Docs-only changes start no test or analysis workflow: set `paths-ignore: ['docs/**']` on `pull_request` and `push`. Workflows that check the pull request itself, such as a release-note check, keep running for docs changes. Check: review of `.github/workflows`.
- **ci-shared-runner.** Self-hosted jobs share one machine and one OS user. Put registry credentials in `COMPOSER_AUTH` on the job or step, never `composer config --global`, which writes the token into config shared by every job of every repository. Run `setup-php`, `setup-node` and `playwright install --with-deps` only with `if: runner.environment == 'github-hosted'`. No service containers (the runner has no Docker); create a database with the runner's own tools. Every job sets `timeout-minutes`. The workflows of `mortelos/starter` run on both kinds of runner and are the example. Check: review of `.github/workflows`.

### Release Notes

Rules for the "Wat is er nieuw" notes an app shows its users (`resources/release-notes/`, package `mortelos/ui` 0.5.42 or newer; format in `docs/components/overlay.md` of `mortelos/ui`). Cite a rule by its name in reviews and pull requests; each rule ends with how it is checked.

- **note-versioned.** An app that ships numbered releases (release branch, merge to `main`, tag) ships `resources/release-notes/<tag>.md` with every release, for example `v0.1.106.md`. The note is part of the release pull request. Check: the deploy check refuses a release without it.
- **note-per-merge.** An app that deploys on every merge to `main` ships, with every merged change a user can notice, its own note `resources/release-notes/<YYYY-MM-DD-HHMM>.md`: 24h, UTC, close to the merge, four digits for the time (`2026-10-25-0930.md`, never `930`). Whoever merges writes it. The id must be newer than every note already on `main` when the change merges: a page only shows notes newer than the newest it loaded with, so an older id is never seen by anyone who loaded the page in between. If `main` got a newer note while the pull request was open, rename yours to the current time before merging. Check: review of the pull request.
- **note-none.** A change nobody can notice (refactor, tests, CI, dependency bump without visible effect) gets no note, and the pull request body says `Release note: geen (<reason>)`. A visible change without a note and without that line is not ready to merge. Check: review of the pull request body.
- **note-format.** A note is plain text: one line per change, starting with `- `. Other lines are paragraphs. No markdown: links, images and formatting show literally. Check: read the file; a name that fits none of the three forms (`vX.Y.Z`, `YYYY-MM-DD`, `YYYY-MM-DD-HHMM`) is ignored by the app.
- **note-tone.** Write terse, plain Dutch for end users: what changed for them, not how. No internal names, ticket or pull request numbers, package names or technical terms. One line per change, as few lines as possible, no em-dashes. Check: review.

Good: `- Je ziet nu bij elke aanvraag wie hem als laatste heeft aangepast.`
Bad: `- Refactor van InboxDetail naar chat::detail (#445).` It says how, not what changed for the user, and names a component and a pull request.

### External Sources And Personal Data

- A package that imports a user's own content from an external service (recorder, mailbox, notes, calendar) owns no tables. Compose framework primitives: the connection is an owned `channels` row, the item is an entity created through `EntityAggregate` events with `owner_user_id`, `visibility=private` and `classification=confidential`, and the text is a `TranscriptImported` event projected into `transcripts`.
- Content is never a hand-written table. Store it in an event and project it; delete it with `TranscriptPurged` plus `RedactStoredEvents`, so a projection rebuild cannot resurrect it.
- Keep provider specifics (OAuth or API client, driver, jobs, pages) in the package and nothing else. Ask before adding any migration to a channel package.
- Reference: `docs/personal-source-channel.md` in `mortelos/framework`.

### Dependency And Versioning

- Publish each MortelOS package as semantic-version tags; bump the minor for breaking changes while the package is below 1.0.
- Require MortelOS packages with caret ranges (for example `^0.5`) resolved from the MortelOS registry (`https://packages.mortelos.com`). Applications commit `composer.lock` so installs are reproducible on CI and in production. Packages keep `composer.lock` out of git so CI tests the newest allowed versions, and state every version floor they rely on in `composer.json`.
- Do not commit local path repositories (such as `../../mortelos/*`) in `composer.json`; they break dependency resolution wherever the sibling checkouts are absent. Develop sibling packages through a local, uncommitted override instead.
- Bump a consumer to a new package version only after that version has a matching release tag.

#### Deploy-safe changes

Pages that were open during a deploy must keep working and no user input may be lost.

- Nothing public on a Livewire component (name, public property, public method, event listener) disappears, renames or changes type in one release. Add the new one, ship, and remove the old one in a later release. `mortelos:livewire-api:check` from `mortelos/dev-tools` warns about this in PRs.
- Migrations are expand/contract: add nullable or defaulted columns first, backfill, switch the code, and drop the old column in a later release. CI blocks destructive migrations unless they are listed in `.mortelos/destructive-migrations.json` or the PR has the label `destructive-migration`.
- Never put `data-mortel-journal="off"` on ordinary text fields; use it only on secrets.

### Laravel Vet

`laravel/vet` guards `composer install`, `require` and `update` in an application: a package version that `vet.json` does not trust fails the command. Only a new dependency is a reason to stop and ask; clear everything else yourself.

- **New dependency: ask first.** Before you `composer require` a package that `composer.json` does not list yet, tell the user which package, what it is for and why the installed packages do not cover it, and wait for a yes. That yes covers the packages it pulls in. Installing or updating a package that is already listed, including `mortelos/*` and `laravel/framework`, needs no question.
- **Clear it with `bin/vet-agent`.** It runs `./vendor/bin/vet` with "Automatically, with my coding agent reading the changes first" and trusts the packages that review passes. Vet has no non-interactive option for that review; `bin/vet-agent` answers its prompts in a pseudo-terminal.
- **Non-zero exit: review the flagged packages yourself.** Vet's review often flags a package that is fine, so do not hand this to the user. `WARN` means the review could not finish (files over the budget, not text, no answer); if the reviewing agent itself failed (rate limit, timeout), run `bin/vet-agent` once more first. `FAIL` means the review saw a possible risk, which is often ordinary code the package needs, such as an HTTP client that calls a URL or a CLI tool that starts a process. For each flagged package, read what vet reported and the files it named, and compare the old and new version on the package's own repository (`gh api repos/<owner>/<repo>/compare/<old>...<new>` and its release notes). Trust it when the change fits what the package is for and matches its repository at that tag. Stop and tell the user in plain words only on a real red flag: obfuscated or encoded code, code that reads `.env`, keys or credentials and sends them somewhere, a download or shell command at install time, a host that has nothing to do with the package, code that is not in its repository at that tag, or a finding you cannot explain. When every flagged package passes, run `bin/vet-agent --trust-all` and list each one in the pull request with what vet flagged and why it is safe. `--trust-all` trusts every package left in the list, so if you stop on one, do not run it for the others.
- Then run `composer install` again and commit `vet.json` with `composer.lock`. Never edit `vet.json` or `vendor/composer/installed.json` by hand, and never run `vet --init` or `vet --fresh` to get past a failure.

### Code Language

- All code is English: names of classes, methods, functions, variables, properties, constants, enum cases, namespaces, files, database tables and columns, array keys, config keys, environment variables, routes, events, Livewire and Blade components, test names, code comments, commit messages and pull requests.
- Use the established English term of the domain, not a word-for-word translation: a Dutch `concept` is a `draft`, the `inhoud` of a mail is its `body`.
- Dutch is allowed only in: text an end user sees (UI copy, mail, notifications, `lang/nl`); the words on the fixed list in `mortelos/dev-tools` (`resources/code-language/allowed-dutch.txt`), such as BSN, KvK, BTW and AVG; and string literals that recognise Dutch input, marked with `code-language: dutch-input <reason>`.
- A session or user language setting decides how you talk to the user. It never applies to code or code comments.
- `CodeLanguageGuard` from `mortelos/dev-tools` enforces this in every repo. Do not weaken it, do not add words to the allowed list in a consumer, and do not use the `dutch-input` marker for names or comments.
- Renaming a public name in a released package is a breaking change: bump the minor version (0.x) and add an upgrade note.

# mortelos/framework
## Agent Runtime Completion Contract

- Do not report an executable OS, app, or package action as completed until the direct tool has succeeded or the runtime has paused for the required approval.
- Do not use `inbox.create` to simulate execution of a missing capability. Use the direct tool when it is listed.

- When `inbox.create` is genuinely appropriate, write clean Dutch proposal copy: a result-oriented title, one complete-sentence summary, and at most two concise body paragraphs. Do not start with "Gebaseerd op" and avoid loose hyphen bullet lists for simple proposals.

## Tenant Lookups From Scripts

- In a script or tinker session, never loop `tenancy()->initialize($tenant)` over tenants: the second tenant throws `TenantIsolationViolation` and raises a production alarm. Switch through `Mortel\Tenancy\Tenants::run()` or `Tenants::each()`.
- For a read-only lookup across tenants on a server, use `php artisan mortel:tenants:inspect <file|->` (see `docs/tenant-isolation.md`).
